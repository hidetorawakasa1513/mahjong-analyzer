## 0. Codexへの最重要指示

この文書は **開発の目的・制約・段階的な実装指示** を定める。未検証の外部仕様を事実として扱わないこと。**最初の作業はPhase 0のみ** とし、Mortalが動くか、雀魂の牌譜を取り込めるか、解析結果を機械的に読めるかを実測する。Phase 1以降を先走って実装しない。確認事項・実施コマンド・結果・失敗理由を `docs/technical-research.md` に記録する。既存のObsidian Vaultや他のリポジトリを許可なく変更しない。

## 1. 背景・目的

ユーザーは雀魂の麻雀成績が伸び悩んでおり、対局後の判断を客観的に振り返りたい。Mortal / mjai-reviewerの既存評価を最大限利用し、**弱点の発生条件と打牌品質の経時変化** を確認するローカルツールを開発する。麻雀AIを自作することそのものは目的ではない。既存ツールにない統計・蓄積・可視化だけを独自実装する。

## 2. 確定済みの要件

- 対象: **雀魂Web版で打った対局終了後の牌譜**。四人麻雀・段位戦を初期の暫定スコープとし、雀魂のルール差・モデルの学習ルール差を調査する。三人麻雀は初期対象外。
- 最初はユーザーが手動で取得した牌譜データを入力。将来的なChrome拡張機能による一括取得に備え、取り込み口を交換可能にする。
- 対局中の支援・リアルタイム解析・相手の非公開手牌や山の情報を利用した評価は **行わない**。評価の基準は意思決定時に利用可能な情報。
- Mortal / mjai-reviewerが担当できる推奨行動・評価結果・Ratingは再発明しない。追加の独自処理は保存・整形・統計・弱点検出・表示。
- 基本指標は **AI一致率、低推奨行動率、Mortal Rating** の3つ。別々に表示し、初期段階で根拠のない独自100点スコアを導入しない。
- 過去期間と直近期間を同一モデル・温度・ルール・データ条件で比較し、サンプル数を併記する。
- 無料・ローカル・オフライン解析を優先。LLM API・課金APIは使用しない。
- 技術候補: Python、SQLite、Streamlit、pytest。実際の要否はPhase 0で調整。
- 個人の牌譜・認証情報・キャッシュ・モデル重みは公開GitHubに誤って入れない。

## 3. 対象外・保留

- 復習問題の自動生成。
- LLMによる戦術解説、モデル内部の判断理由の断定。
- 最新麻雀戦術のWeb定期収集（将来検討）。
- Chrome拡張機能の開発・自動一括ダウンロード（将来検討）。
- 日本語TTS・J.A.R.V.I.S.風音声アシスタント（将来検討）。
- 麻雀判断AIの再学習・完全自作（既存AIで不足が明確になったときのみ再検討）。
- インターネットへの対局データ公開、常時稼働サーバー、サブスクリプション等。

## 4. 参照実装と調査ポイント

- Mortal: https://github.com/Equim-chan/Mortal （コードはAGPL-3.0系、配布・再利用時の確認必須）
- mjai-reviewer: https://github.com/Equim-chan/mjai-reviewer
- エンジン出力: `src/review/mortal.rs` に `total_reviewed`, `total_matches`, `rating`, `temperature`, `kyokus`, `model_tag`、各 `Entry` に `junme`, `expected`, `actual`, `is_equal`, `details`, `shanten` 等、各 `Detail` に `q_value`, `prob` が定義されている。**本番で出るJSONの構造・キー・版数はサンプル実行で確認する**。
- CLIにJSON出力の `--json` オプションが存在する。具体的な入力・出力引数は導入したバージョンの `--help` で確認する。
- mjai-reviewer READMEは雀魂Web版向けWebアプリを案内する一方、ローカルCLI例は天鳳形式が中心。**雀魂Webからユーザーが合法的に取得できる牌譜ファイル形式とローカル変換方法は未検証**。
- Mortalのモデルのルール前提と雀魂のルールは必ずしも同じでない。スコアや順位評価の解釈に注意。
- MortalのQ値・softmax確率は実際の点棒損失や客観的悪手度を直接示さない。AI推奨行動も絶対的な最善手とは限らない。

## 5. システム設計方針

```text
[手動取得した牌譜]   [将来: Chrome拡張機能]
          │                    │
          └────────┬───────────┘
                   ▼
             Import Adapter
       (形式検証・変換・重複排除)
                   ▼
           Raw Logs / SQLite
                   ▼
         Mortal + mjai-reviewer
                   ▼
          Raw Review JSON保存
                   ▼
       Normalizer / Metric Engine
                   ▼
        Weakness / Trend Engine
                   ▼
        Streamlit Dashboard
                   ▼
      [将来: レポート文面 → TTS]
```

**責務分離:** `importer`（入力）、`review_runner`（既存AIの実行）、`normalizer`（JSONとデータモデルの橋渡し）、`metrics`（計算）、`analysis`（集計）、`ui`（表示）。評価エンジンへの接続はアダプタ化し、Mortal更新時に弱点分析コードを変更せずに済むようにする。

**永続化:** 元の牌譜（許可されたデータのみ）および生のレビューJSONを保全。SQLiteには取り込み元・ハッシュ・対局ID・対象プレイヤー・ルール・対局時刻・モデルタグ・温度・レビュー版・分析条件・個々の意思決定データを保持。IDが利用できない場合の重複判定は内容のハッシュで実施。再実行・失敗時にも二重登録しない。

**安全性:** 自動ログイン、通信盗聴・非公開APIへのアクセス、認証トークンの収集・再利用などはPhase 0では禁止。データ取得に規約や権利の不明点が残れば取り込まず、障害として報告する。

## 6. 指標定義（初期案）

1. **AI一致率** = `total_matches / total_reviewed`。局面数・対象行動の定義を既存Reviewerと合わせる。0件の場合は `N/A`。
2. **低推奨行動率** = `選択した行動のprobが閾値未満の件数 / 比較可能な行動数`。**デフォルト閾値は暫定5%**、ユーザーが設定可能。`actual_index` や `actual` と `details` の対応関係を実データで検証する。欠損・比較不能を母数に含めない。softmax温度・モデル版が変われば横比較しない。UIに「悪手率ではない」と注記。
3. **Mortal Rating** = mjai-reviewerが出力した値を、**既存の定義とスケールのまま** 表示する。勝手に100倍・正規化しない。期間統合が可能かは算出式・集計単位を確認し、安易に半荘Ratingの単純平均を「統合Rating」としない。

初期分析軸は巡目帯、東場/南場、親/子、対戦相手のリーチ有無、局面のシャンテン数、点数状況など。ただし**対象となる意思決定時点の状態をJSON等から再現できるものに限る**。リーチ後・押し引きなどのカテゴリ付与は状態遷移を慎重に検証し、曖昧なら「推定」または「非対応」と表示。

成長比較は、同じ設定の過去N半荘対直近N半荘、もしくは期間指定で計算。評価行動数・期間・モデル・ルール条件・未評価件数を提示する。改善断定を避け、少数サンプルは「参考値/データ不足」とする。将来は状況構成を補正した比較や不確実性区間を検討する。

## 7. フェーズと受け入れ条件

### Phase 0 — 先に実施する技術検証

- 開発環境のOS/アーキテクチャ、Python/Rustの状況を **読み取りのみ** で確認。
- Mortalとmjai-reviewerの最新資料を確認し、必要なライセンス・モデル重みの利用条件を文書化。
- Apple Silicon macOSで既存の推論エンジンを起動できるか検証。依存関係を導入する場合、プロジェクト内の分離環境で実施し、全体の環境変更は事前相談。
- **雀魂Web版からの手動取得手段**、取得形式、実際にユーザーが持つサンプルの取り込み可否を確かめる。素材がなければ合成/公開サンプルで入出力試験し、本物の雀魂牌譜での検証は未完了とする。
- JSON出力を取得し、3指標の生データ、局面情報、モデル・温度の保存可能性を確認。
- `docs/technical-research.md` に「確認済み」「推測」「未検証」「ブロッカー」を分離して記録。
- **受け入れ条件:** サンプル1件の対局後レビューをローカルでJSON保存し、3指標を（必要なデータがあれば）表示できる。不可の場合は再現手順と代替案を提示して停止。

### Phase 1 — 牌譜取り込み・保存

- 複数ファイルの読み込み、形式検証、重複排除、エラー処理、SQLite保存。
- 対局者を特定できるIDや席番の検証。誤認したレビューを保存しない。
- 生データを保全し、同じデータを再投入しても重複しないことをテスト。

### Phase 2 — 3指標・行動ごとの集計

- MortalレビューJSONを正規化して保存。比較不可能・欠損値を記録。
- AI一致率、低推奨行動率、Ratingの再現性を検証。
- 巡目・局面別集計を追加し、対象行動数を必ず表示。

### Phase 3 — 弱点と成長のダッシュボード

- 画面A: 3指標の概要と時系列、画面B: 局面別の弱点傾向、画面C: 対局・レビュー履歴。
- 一致率と低推奨行動率の低下が見られる局面を「優先確認候補」として表示。原因を断定しない。
- 同一評価条件の比較とデータ不足メッセージを実装。

### 将来（今回実装しない）

Chrome拡張機能 / 一括牌譜取得、TTS音声案内、Web戦術記事の週次情報収集、独自の総合採点モデル、他AIの比較。

## 9. Codexへの最初の実行指示（このまま貼り付け可能）

> `docs/CODEX_SPEC.md` を読み、**Phase 0だけ**実施してください。まず既存環境を読み取り専用で確認し、Mortal・mjai-reviewer・雀魂牌譜形式の現行仕様を公式資料・ソースコードで調べてください。牌譜取得やMacでの動作は未確認として扱い、安全な手動取り込み方法と代替案を比較してください。サンプルが利用できれば1件のJSONレビュー出力を検証し、3指標の計算・モデル設定保存の可否を確認してください。依存関係の導入やOS全体の変更は勝手に行わず、許可が必要な内容を明記してください。`docs/technical-research.md` に出典・検証日・実施コマンド・環境・結果・未解決事項・Phase 1へ進めるかの判定を書いてください。実証のないまま成功と報告しないでください。
