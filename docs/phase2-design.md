# Phase 2-A：局面データ・分析可能性の調査

## 1. 目的と範囲

Phase 2-Bで統計分析と局面復習を実装する前に、Phase 1.5で保存したレビューJSON、MJAI、Tenhou/6 JSON、元の天鳳`.mjlog`から、判断時点の情報を安全に復元できるかを調査した。

本調査は読み取り専用で実施した。既存のSQLite、レビューJSON、MJAI、`.mjlog`、本番コード、CLI、SQLiteスキーマは変更していない。天鳳サーバーへの通信、Mortalの再実行、依存パッケージの追加も行っていない。

### 確認した範囲

- 既存の2レビュー、合計301判断
- レビューJSONに埋め込まれたMJAIイベント列
- 変換後Tenhou/6 JSON
- 対応する元の天鳳gzip XML
- `games`、`reviews`、`decisions`の現行スキーマとインポーター

個人名、対局ID、個別の牌譜内容、個別レビュー値はこの公開ドキュメントに記載しない。詳細な実測値は指定されたObsidianの非公開ログに記録する。

## 2. 現行データの構造

現行の`decisions`は、`review_id`、平坦化した`decision_index`、`kyoku_index`、`junme`、`shanten`、実際・推奨行動、比較結果、実際の行動確率を保持する。`decision_index`はレビュー配列を平坦化した番号であり、MJAIやXMLのイベント位置ではない。また、`kyoku_index`はレビュー内の局配列の位置であって、元XMLのノード番号でもない。

レビューJSONには、次の局面情報が既に存在する。

- `review.kyokus[]`: 局番号、本場、局開始時の相対点数、局終了状態
- 各エントリ: `junme`、残り牌、直前に行動した座席、ツモ牌、手牌、`fuuros`、各種状況フラグ、向聴数
- 各エントリの`actual`/`expected`と候補別`details[]`
- トップレベルの`mjai_log`: `start_kyoku`から終了までのMJAIイベント列

したがって、Phase 2-Bの最初の実装では、同じレビューJSONから復元できる情報を優先し、Mortalを再実行しない方針が妥当である。

## 3. 判断と牌譜イベントの対応づけ

### 調査方法

単純な`actual`の文字列検索は使わず、次の順序付き対応づけを行った。

1. `start_kyoku`の順序でMJAIを局単位に分割する。
2. レビューの`kyokus[]`と同じ局順で対応させる。
3. 局内で、レビューの`actual`をイベント種別、座席、牌、対象座席、消費牌、副露内容などで比較する。
4. 直前に対応づけたイベントより後ろから、次に出現する一致イベントだけを採用する。
5. `actual.type == "none"`は実イベントを表さないため、イベント位置を割り当てない。

これにより、同じ牌を何度も打つ局面でも、局・順序・状態遷移を保持した対応づけになる。将来保存する`source_event_index`は、局内ではなくMJAI全体の0始まりイベント番号とし、局内イベント番号も併記できるようにする。

### 実測結果

| 分類 | 件数 | 判定 |
|---|---:|---|
| レビュー判断の総数 | 301 | 既存DBの判断数と一致 |
| 実MJAIイベントに対応づけられた判断 | 251 | 順序付き対応で一意 |
| `none`（レビュー上の非行動エントリ） | 50 | 実イベント位置なし。未対応ではなく非イベントとして扱う |
| 順序付き対応後の未対応 | 0 | 今回の2レビューではなし |
| 順序付き対応後の曖昧な採用 | 0 | 次のイベントを順序で一意化 |

一方、局内で条件に合うイベントを順序制約なしに検索すると、同一行動が複数候補になるケースが合計45件あった。これは単純な行動文字列一致を採用してはいけない根拠である。

実イベントに対応した行動には、通常打牌だけでなく、レビュー対象プレイヤーのチー、ポン、暗槓、加槓、リーチ、和了も含まれていた。`none`を鳴かなかった回数や見送り機会として再解釈してはならない。

### Tenhou/6 JSONと元XMLとの関係

ConverterのTenhou/6 JSONは局単位の開始情報、ツモ、打牌、鳴き、リーチ、結果を持つが、現行SQLiteにはそのイベント位置が保存されていない。元XMLも`INIT`、牌操作タグ、`N`、`REACH`、`AGARI`、`RYUUKYOKU`などの順序は保持しているが、Converterが生成したMJAIイベント番号との対応表は別途計算する必要がある。

Phase 2-Bでは、レビューJSONのMJAI列を主な対応元とし、次のハッシュを保存して入力の同一性を検証することを推奨する。

- 元`.mjlog`のSHA-256
- 変換後Tenhou/6 JSONのSHA-256
- MJAIログの正規化SHA-256
- 抽出器バージョン

対応が再現できない場合は、`source_event_index`を推測せず、`context_status = 'unmapped'`として残す。

## 4. 巡目の定義

`junme`は既存Reviewerが付与した判断時点の値であり、通常の打牌だけでなく鳴き、リーチ、和了、`none`にも付く。これは単純な「本人の打牌回数」と同一とは限らない。

Phase 2-Bでは次の2種類を分離する。

- `turn_number`: 判断対象プレイヤーの局内の判断・ツモ進行に対応するReviewerの`junme`。既存レビューとの整合性を優先する。
- `source_event_index`: 実際のMJAIイベント位置。鳴き、リーチ成立、槓、嶺上ツモを含む全イベントの時系列位置。

通常打牌、鳴き直後の打牌、リーチ宣言に伴う打牌、槓後の嶺上ツモは、イベント列では区別できる。鳴かなかった判断はReviewerの`none`を根拠に追加しない。

初期の集計帯は仕様どおり、1〜6を序盤、7〜12を中盤、13以降を終盤とする。ただし、`junme == 0`の非行動エントリは帯集計から除外する。帯境界は設定値として扱い、スキーマに固定値を埋め込まない。

## 5. 向聴数と手牌

判断エントリの`state.tehai`と`state.fuuros`から、判断直前の自分の公開可能な状態を取得できることを確認した。通常打牌のエントリではツモ後の手牌が入り、`fuuros`は副露を表す。赤牌は牌名の赤表現を保持しているため、通常牌と同一種として数える処理と赤牌表示を保持する処理を分ける必要がある。

現行の`shanten`はReviewerがそのエントリに対して算出した値である。今回の実測範囲では0〜5の値が確認でき、`state`と同じレビューJSONから取得できる。したがって、Phase 2-Bの一次値はReviewerの`shanten`を使用し、独自計算を分母や既存指標に混ぜない。

通常手、七対子、国士無双を独自に再計算する処理は今回実装していない。独立検算が必要になった場合は、まず既存OSSのライセンス、赤牌、鳴き、暗槓・加槓、手牌枚数の扱いを確認し、追加依存を導入せずに済むかを判断する。Reviewer値と独自値が異なる場合は、どちらかを黙って上書きせず、計算方式と差異を記録する。

## 6. 他家リーチ状態

MJAIには`reach`と`reach_accepted`が別イベントとして存在する。判断時点の「成立済みリーチ」は`reach_accepted`を基準にする。`reach`だけを見て成立済みと数えると、宣言直後のロンなどの境界を誤る可能性がある。

推奨する状態は次のとおり。

- `opponent_riichi_count`: 判断直前までに`reach_accepted`を受けた他家の人数
- `riichi_seats`: 成立済みリーチの座席集合
- `self_riichi`: 本人の成立済みリーチ状態
- `reach_declaration_pending`: `reach`後、`reach_accepted`前の中間状態（必要な場合のみ）

供託は点数状態の一部として扱い、リーチ宣言イベントを二重に数えない。ダブルリーチ、複数リーチ、宣言牌での和了はイベント順序で処理する。今回のレビューJSONの`at_self_riichi`や`at_opponent_kakan`は補助的なReviewer状態として保存できるが、座席集合はMJAIイベントから再構成する方が明確である。

## 7. 点数・順位・点差

レビュー局データの`relative_scores`は局開始時点の4人の点数であり、局終了時の`end_status[].deltas`も取得できる。しかし、既存の判断エントリには判断直前の4人の点数は直接入っていない。

判断直前の点数を得るには、局開始点を初期値として、少なくとも次を時系列で適用する必要がある。

- `reach_accepted`に伴う供託・リーチ棒
- 和了・流局の結果差分
- 本場、親・子、連荘による局遷移
- 次局の`start_kyoku.scores`との整合性

局中の判断は結果イベントより前に発生するため、局開始点とその時点までの成立済みリーチによる支払いを主に追跡する。結果イベントを先に適用してはならない。原始データとして4人の符号付き点数ベクトルを保存し、順位や点差はそこから再計算する。

順位は同点時の天鳳固有の並び順を今回の調査では確定していない。Phase 2-Bでは、まず`rank_before`をNULL許容とし、同点ポリシーと根拠を確定してから値を有効化するのが安全である。`gap_to_first`、`gap_to_last`、直上・直下との差も、符号付き整数の点数ベクトルから決定的に算出する。集計区分は一次データを失わないよう、固定の点差帯ではなく後段の設定で行う。

## 8. 行動種類と分母

Reviewerが実際に記録した行動だけを分類対象にする。

| カテゴリ | 判定根拠 | 初期対応 |
|---|---|---|
| `discard` | `actual.type == 'dahai'` | 対応 |
| `riichi` | `actual.type == 'reach'`、またはリーチに続く実打牌 | 対応。ただし宣言と打牌を二重に数えない定義が必要 |
| `chi` / `pon` | `actual.type` | 対応 |
| `ankan` / `kakan` / `daiminkan` | `actual.type` | 対応可能なものを個別保持 |
| `hora` | `actual.type == 'hora'` | 対応。打牌指標の分母からは分離 |
| `none` | `actual.type == 'none'` | 非行動エントリ。見送りと解釈しない |

「鳴かなかった機会」はReviewerのJSONに明示されていないため、Phase 2-Bの鳴き率の分母へ推測で追加しない。低推奨行動率やAI一致率も、現行Reviewerがレビューしたエントリ定義と分母を維持する。

## 9. 局面復習に必要な表示情報

復習画面で利用する候補情報は、次のように公開情報と非表示情報を分ける。

### 表示してよい情報

- 対局・局・本場・親
- 判断のイベント位置、巡目、残り牌
- 本人の判断直前の手牌と副露
- 各プレイヤーの河と公開副露
- ドラ表示牌、成立済みリーチ座席
- 判断直前の4人の点数、順位、点差
- 実際の行動、Mortalの候補行動、確率、Q値

### 表示・分析に使わない情報

- 判断時点で見えていない他家の手牌
- まだ引かれていない山の中身
- 解析後にだけ分かる結果を判断材料として扱うこと

MJAIの`start_kyoku.tehais`は変換ログとして全座席の開始手牌を含むため、保存場所がローカルでも、復習表示用のDTOやAPIで全手牌をそのまま返さない。レビューJSONの`state`と公開イベントから構成した局面を表示用の正本とする。

## 10. SQLite拡張案

既存の`games`、`reviews`、`decisions`は変更せず、1判断に対する抽出結果を別テーブルに保存する。

### `decision_contexts`案

| カラム | 型案 | 内容 |
|---|---|---|
| `id` | INTEGER PK | コンテキスト行ID |
| `decision_id` | INTEGER FK | 既存判断への参照 |
| `extractor_version` | TEXT | 抽出ロジックの識別子 |
| `context_status` | TEXT | `complete` / `partial` / `unmapped` / `invalid` |
| `source_event_index` | INTEGER NULL | MJAI全体の論理イベント番号 |
| `source_round_event_index` | INTEGER NULL | 局内イベント番号 |
| `round_index` | INTEGER NULL | 局配列の位置 |
| `bakaze` / `kyoku` / `honba` | TEXT/INTEGER | 局識別情報 |
| `turn_number` | INTEGER NULL | Reviewerの`junme`を正規化した値 |
| `shanten_before` | INTEGER NULL | 判断直前のReviewer値 |
| `action_category` | TEXT NULL | 行動カテゴリ |
| `is_dealer` | INTEGER NULL | 親フラグ |
| `opponent_riichi_count` | INTEGER NULL | 成立済み他家リーチ数 |
| `riichi_seats_json` | TEXT NULL | 成立済み座席集合 |
| `scores_before_json` | TEXT NULL | 4人の符号付き点数 |
| `rank_before` | INTEGER NULL | 順位。同点規則確定までNULL可 |
| `gap_to_first` 等 | INTEGER NULL | 点差。一次点数から算出 |
| `source_sha256` | TEXT NULL | 入力ログの同一性確認 |
| `extraction_note` | TEXT NULL | 部分復元・未検証理由 |

主キーとは別に`UNIQUE(decision_id, extractor_version)`を置く。同じレビューを新しい抽出器で再計算でき、旧結果も比較・再現できる。`context_status`が`partial`や`unmapped`の行を集計へ自動投入せず、対象数と除外数を表示する。`source_event_index`、`action_category`、`turn_number`、`shanten_before`、`opponent_riichi_count`にインデックスを付ける。

将来的に局面復習を高速化する場合は、解析条件・入力ハッシュを持つ局イベントキャッシュを別テーブルに分けてもよい。ただし、Phase 2-Bの最初の実装では、既存レビューJSONから一度抽出して`decision_contexts`へ保存する構成で十分である。

## 11. 集計案

基本3指標の分母は変更せず、次の軸を追加する。

- 巡目帯
- 東場・南場、局番号
- 親・子
- Reviewerの向聴数
- 成立済み他家リーチの有無・人数
- 点数順位と点差帯（4人の生点数は常に保持）
- 行動カテゴリ

各集計には`review_count`、`comparable_count`、`agreement_count`、`low_recommendation_count`、`missing_context_count`を併記する。サンプル数が少ない区分は数値だけで弱点と断定しない。Mortal Ratingは現行仕様どおりレビュー単位で保持し、半荘のRatingを単純平均しない。

## 12. 品質チェック

Phase 2-Bの抽出器は、保存前に最低限次を検証する。

1. `decisions`の件数と抽出対象件数が一致する。
2. `none`が見送り件数として集計されていない。
3. `source_event_index`が局・MJAI列の範囲内である。
4. 同一判断へ複数の抽出結果を作らず、抽出器バージョンで再計算を分離する。
5. 手牌・副露の牌枚数がイベント遷移と矛盾しない。
6. 赤牌、チー、ポン、暗槓、加槓、嶺上ツモ、リーチ、和了、流局を含む局で状態が破綻しない。
7. `reach`と`reach_accepted`を混同しない。
8. 局開始点、供託、結果差分、次局開始点の点数が整合する。
9. 他家の非公開手牌や未公開山牌を表示用データへ流さない。
10. 取得不能な値を推測せず、NULLと理由を保存する。

## 13. 事実・推奨・未検証事項

### 確認済みの事実

- 既存2レビュー、301判断を読み取り専用で検査した。
- レビューJSONにMJAI列と判断直前の手牌・副露・Reviewer向聴数がある。
- 順序付きイベント対応で、実イベント251件を未解決なく対応できた。50件は`none`で実イベントを持たない。
- 局開始時点の相対点数と局終了差分はレビューJSONから取得できる。
- 成立リーチを表す`reach_accepted`は`reach`と別イベントである。
- 現行SQLiteの`decisions`にはイベント位置、点数、リーチ座席、公開河の専用列がない。

### Phase 2-Bへの推奨

- `decisions`を変更せず、バージョン付き`decision_contexts`を追加する。
- レビューJSONに埋め込まれたMJAIを一次対応元とし、元`.mjlog`と各変換物のハッシュを保持する。
- Reviewerの`junme`とMJAIのイベント位置を別フィールドで持つ。
- Reviewerの向聴数を一次値とし、独自計算は検算用に限定する。
- 点数は4人の生ベクトルを先に保存し、順位・点差を後段で算出する。

### 未検証・保留

- 天鳳の同点時順位をMahjong Analyzerの順位定義として採用する根拠。
- 全種類のルール差異を含む牌譜での点数再構成。
- `junme`の全境界ケース（ダブルリーチ、宣言牌和了、複数槓、複数局継続）での意味の完全な仕様化。
- 七対子・国士無双を含む独立向聴数計算とReviewer値との差異。
- 既存のConverter出力から元XMLノード位置を恒久的に一意化する共通マッピング仕様。

Phase 2-Bでは、上記の保留事項を埋められない情報については、成功扱いにせず`NULL`と抽出状態で明示する。
