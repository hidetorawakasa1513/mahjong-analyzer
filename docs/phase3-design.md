# Phase 3-A〜3-B①：Streamlitダッシュボード設計

## 目的

Phase 2-B〜2-Cで実装した集計・復習候補・局面復元APIを、ローカルのStreamlit画面から利用する。ダッシュボードは分析結果の閲覧と復習対象の選択を担い、Mortalの実行や牌譜の取得は行わない。Phase 3-B①では日常利用向けの共通条件・表示・ページングを改善する。

## 画面構成

### ホーム

`games`、`reviews`、`decisions`と既存の`summary()`から、解析済み半荘数、対象判断数、AI一致率、低推奨確率の選択率、AI不一致数を表示する。評価条件ごとの指標とMortal Ratingもレビュー単位で表示し、異なるモデル・温度・ルール条件を無条件に混ぜない。

### 状況別分析

`analytics.aggregate_contexts()`を呼び出し、巡目帯、向聴数、他家リーチ人数、順位、点数差、行動種類、場風、親子、局番号、本場を表示する。評価条件を1つ選択してから集計し、複数レビューの比率は分子・分母を合算する。グラフは判断数、AI一致率、低推奨選択率を切り替え、選択した分類と条件を復習候補へ渡す。

### 復習候補

`review_candidates.list_review_candidates()`を呼び出し、低推奨確率順、不一致優先、新しい対局順を選択する。既存の条件フィルタを再利用し、`none`も除外しない。技術列を通常表から分離し、候補の`decision_id`を選択して局面詳細へ遷移する。ページ番号と総件数を表示し、条件変更時は1ページ目へ戻す。日時不明時は「日時不明」とし、ファイル更新日時を使わない。

### 局面詳細

`review.get_review_scene()`を呼び出し、判断直前の手牌・副露、公開河、公開副露、ドラ表示牌、リーチ状態、点数、Mortal候補をテキストとJSONで表示する。通常行動はイベント処理前、`none`は参照した公開打牌後の状態であることを表示する。順位は同点時に未確定とする。他家の非公開手牌や未公開の山牌は表示しない。

## 状態管理

画面は`st.session_state["page_selector"]`で切り替える。ボタン遷移は`navigation_target`を一時的に保持し、Streamlitウィジェットのキー衝突を避ける。状況別分析から候補一覧へ遷移するときは`candidate_filters`を保存し、候補から局面詳細へは`selected_decision_id`を保存する。候補条件の変更時はページングの開始位置を0へ戻す設計をPhase 3-Bで強化する。現在のMVPではページ位置は画面入力で明示する。

## データ接続と安全性

`dashboard.data.connect_readonly()`はSQLite URIの`mode=ro`と`PRAGMA query_only=ON`で既存DBを開く。ファイルが存在しない場合は作成せず、画面に不足を表示する。レビューJSONと元牌譜のルートは画面のローカル設定欄から指定し、外部通信やクラウドAPIは使用しない。

## 起動

```bash
.venv/bin/pip install -e '.[dashboard]'
.venv/bin/streamlit run app.py --server.address 127.0.0.1
```

`local_data/config.json`の`dashboard`設定をプロジェクトルート基準で解決する。実データをGit管理対象へ移動・複製しない。設定がない場合は従来の`local_data/mahjong_analyzer.sqlite3`等へフォールバックするが、存在しないDBを作成しない。

## 今後のPhase 3-B以降

### Phase 3-B②準備：牌素材

`assets/tiles/`にはMJAI識別子に対応する37種類の自作SVGと`preview.html`を置く。`scripts/generate_tile_assets.py`から再生成でき、外部素材・CDN・スクリプトを参照しない。現段階では素材のプレビューまでとし、局面詳細画面への組み込みはPhase 3-B②で行う。

#### 牌画像改善：代表牌プロトタイプ

実物の日本式リーチ麻雀牌に共通する、縦長の白〜乳白色の牌面、薄い縁取りと内枠、控えめな影、スートごとの色分け、赤五の目印を参考に、`scripts/generate_tile_prototypes.py`で16種（1/5/9の各数牌、代表字牌、赤五）を独自SVGとして試作する。外部画像は成果物に含めない。既存の37種のうち試作対象だけを更新し、残り21種は従来素材のまま保持する。

試作の見た目確認には`assets/tiles/prototype-preview.html`を使う。全37種への展開と局面詳細画面への組み込みは、デザイン確認後に行う。

### Phase 3-B②：麻雀王国牌画による局面表示

麻雀王国の牌画カテゴリに掲載された利用条件を確認し、47×63の縦向き牌画1を第三者素材として隔離した。通常の数牌27種と字牌7種を`assets/third_party/mj_king/tiles/`に保存し、`src/mahjong_analyzer/tile_assets.py`でMJAI識別子から固定マッピングする。画像パスは許可された識別子からだけ解決し、任意パスを受け付けない。

47×63の4セットには赤五が含まれなかったため、赤五3種は通常5牌へ代用せず、元画像を保持したまま`scripts/create_red_tiles.py`で牌面の濃色部分だけを赤系へ変換した派生画像を生成する。派生画像であることと加工方法は`assets/third_party/mj_king/README.md`に記録する。局面詳細では、復元済みの手牌・ツモ・副露・河・ドラ表示牌・リーチ・点数・Mortal候補を画像表示し、非公開手牌は表示しない。開発用の詳細JSONは折りたたみで残す。

### Phase 3-C①：赤五と卓面型の局面詳細

`assets/third_party/mj_king/tiles/5mr.gif`・`5pr.gif`・`5sr.gif`は、公式の通常5牌を加工したローカル派生素材である。再生成は次のコマンドで行う。

```bash
.venv/bin/python scripts/create_red_tiles.py
```

局面詳細は`src/mahjong_analyzer/table_view.py`の相対座席・公開情報整理を利用し、左側に卓面、右側にMortal評価と判断ナビゲーションを配置する。対局時点で公開されていない他家手牌は表示せず、レビューJSONの詳細は折りたたみで確認できる。`turn_number`、点数、ドラ、リーチ状態、河、副露、本人の手牌・ツモを既存の復元データから表示する。

### Phase 3-C②-B：実データ卓面UI

局面詳細は`get_review_scene()`の結果を`dashboard.table_renderer`へ渡して描画する。本人を下、下家を右、対面を上、上家を左へ相対変換し、河全体を6列グリッドとして回転する。副露は河とは別領域に配置する。HTML描画はSQLiteへアクセスせず、牌画像は固定マッピングされたローカル素材をBase64で埋め込む。判断ナビゲーションはStreamlitネイティブボタンを維持する。

リーチ宣言牌・鳴かれた捨て牌はMJAIイベント列で確認できる場合だけ注記する。元データにない物理牌位置や鳴き元は推測しない。暗槓の裏面素材は現時点で未収録のため、裏面を示すプレースホルダーを表示する。

### Phase 3-C③：副露方向と評価候補の改善

副露はプレイヤー本人の視点を基準に描画し、通常牌は副露全体の回転だけで同一方向を保つ。`target`が復元できるチー・ポン・大明槓・加槓では、鳴いた牌を左・対面・右の対応位置へ置き、黄色枠とツールチップで鳴き元を示す。`target`がない暗槓は裏面プレースホルダーを使い、鳴き元を推測しない。

Mortal評価は候補を確率順に並べ、上位3件を常時表示し、4件目以降をHTMLの`details`要素による「もっとみる」に収納する。SQLite、Mortal実行、評価指標の定義は変更しない。描画層は公開情報のみを受け取り、外部画像・外部通信を使用しない。

### Phase 3-C④：副露配置と重なりの改善

副露は河や中央情報の位置から算出せず、各座席の手前側にある専用領域へ配置する。画面上では、上家・対面・下家・本人の各`ma-melds-*`領域を分離し、本人の手牌と副露の間隔を`--hand-meld-gap`として調整可能にする。通常の手牌は非公開情報を含む他家には描画せず、他家の領域は公開副露の配置基準としてのみ使用する。

河は上下中央帯・左右側帯、局情報は中央の予約領域、本人の手牌と凡例は下部の別領域に置く。これにより河・副露・局情報・凡例が同じ領域を奪わないようにする。狭い画面ではCSSメディアクエリで牌と卓の高さを縮小し、評価候補は既存の上位3件＋「もっとみる」を維持する。SQLiteと解析結果は読み取り専用で変更しない。

卓面は正方形に近い縦長寸法を基準にし、河は6列・最大3段を持つ上下左右の帯へ配置する。中央パネルは河の帯の内側にある中央領域へ置き、凡例は卓面の外側へ分離する。参考資料`雀卓.svg`のほぼ正方形の比率と中央・四方向の配置構造を設計上の参考にしたが、SVG内の牌図形や座標は成果物へコピーしていない。

その後の河調整では、河牌を`--kawa-tile-width: 36px`・`--kawa-tile-height: 48px`、6列×最大3段の固定ブロックとして扱う。河の枚数によって牌を縮小せず、`--kawa-block-width`・`--kawa-block-height`で先に専用領域を確保する。自分の河は下側の固定帯へ移し、中央情報・手牌・副露と重ならない余白を優先する。画面が狭い場合も河牌寸法は変更せず、卓面の縦スクロールで対応する。

### 河・中央情報・点数ラベルの位置調整

河の固定ブロック寸法は維持し、点数ラベルを河ブロックの外側にある専用位置へ移動する。左右のラベルは左右の河の外側、対面・本人のラベルは上下の河との間に置き、河の枚数に応じて位置を変えない。中央情報は中央予約領域だけを使用するため、4方向の河を覆わない。描画要素には`data-testid`を付与し、合成局面を使ったPlaywright衝突検査を任意テストとして実行できるようにした。Playwright未導入環境ではこの検査はスキップされ、通常のpytest/AppTestには影響しない。
